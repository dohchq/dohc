# Share links implementation plan

Reader: the agent or person implementing the share links program, one phase at a time. Each phase names what it builds, what it must settle first, and the gate that ends it. Do not start a phase before its predecessor's gate passes.

The design is recorded in `CONTEXT.md` (vocabulary) and `docs/adr/0001` through `0006` (decisions). The full adversarial design review that shaped this sequencing is `docs/plans/share-links-review-2026-08-24.md`; consult it when a phase's threat detail here feels thin. Design summary in one paragraph: a share link is a URL-shaped grant on an existing share (View, Comment, or Edit; revocable, retunable, rotatable), served to accountless link holders by a new public service `services/share-web`, backed by the relay replica for availability, with multiplayer live-document editing under a single configured session host, and owner-approved app publications on isolated origins. Everything ships in staged slices of one final model; nothing here is a temporary contract.

## Phase 0: contracts

Build the data and authorization contracts before any route or UI.

- Replace the one-row share model with share, grant, and link credential records (ADR 0005) in `packages/security-contract`. Grant and credential persistence records stay relay-side per ADR 0005; only `GrantBinding` crosses the engine boundary (a device session host checks it), so only it gets a Rust twin held equal by shared vectors.
- The normalization covers chat-channel grants in the same table: a channel grant keeps its read-only or read-write access, typed by the share's selector kind, on the grant. No second access location survives. Channel shares still never get public links in this program.
- Define grant generations and the `{grant, generation, access}` binding for every derived credential.
- Define one `authorizeShareAction` seam owned by the relay: server-derived principal, action, resource in; effective capability or generic refusal out. Callers never combine link, selector, approval, and policy rules themselves. The seam reloads the share's active status and the granter's current standing on every check; deleting a share revokes every grant.
- Define the link principal (server-minted, per link grant per browser) and the audit record that survives Y.Doc compaction, replication, and settlement.
- Define host lease, epoch, and append-before-acknowledge journaling shapes (ADR 0003), and the publication record (ADR 0006).

Settle first: what derived named grants survive; what the owner can inspect, block, and delete from the audit record. Already settled: one share can hold several link grants at mixed levels — the model enforces no cap, and the UI may surface one link without constraining the model; no expiry in v1 (the state machine refuses it; owners revoke instead), and selector scope is immutable after share creation — a different scope is a new share, so no transition can silently widen what a leaked URL reaches.

Gate: contract tests pass in both languages; a written state machine for grant transitions (create, narrow, widen, rotate, revoke, expire, convert, promote) with no undefined transition.

## Phase 1: prototypes

Prove the failure cases before committing to implementation shape. Each prototype is throwaway code with a written result.

1. **Credential lifecycle. DONE for HTTP View.** Fragment exchange, protected viewer sessions, generation-bound reads, rotation, revocation, and active blob termination pass. Relay and `share-web` logs exclude bearer secrets, the viewer removes the fragment from its address and history, referrers are disabled, and viewer responses use `private, no-store`. Self-hosted deployments must not put a caching proxy in front of `share-web`. Phase 4 owns link WebSocket closure and stale-generation commit races.
2. **Stop-and-restore.** DONE — verdict: viable with constraints (docs/plans/share-links-restore-prototype-2026-08-24.md). The restore is an update on the same lineage, never a direct merge from an old lineage. Constraints Phase 4 must encode: grant invalidation precedes the restore write atomically; accepted post-restore-point work the vandal deleted is stated as lost; a reconnecting client's pre-restore-based delta is quarantined for explicit review and reapplication rather than merged silently, because the prototype showed surviving bytes land at wrong positions; and the host guards merged stale deltas against journal provenance, because a permitted client can resurrect a fenced author's history — the gate races exactly that reconnect and covers the offline-editor case.
3. **Selector drift. DONE for View reads.** Each read derives authority from the current projected namespace. Move, deletion, and different-object recreation refuse superseded digests. Responses use `private, no-store`, and traversal cannot escape the projection. Phase 4 owns append-time access, selector, and generation races.
4. **Browser isolation. DONE for the viewer origin.** The real-browser suite covers active formats, navigation, remote fetches, service workers, storage, cross-origin requests, and viewer credentials. The handoff custom header forces an ungranted preflight. App-origin and cross-app storage attacks remain Phase 5 work against the publication origin model.
5. **Anonymous load. DONE for settled View.** Phase 2 bounds current-state listing, forward replay, concurrent blob memory, slow-consumer backpressure, request rates, and authenticated shared-content egress without charging owner sync. Phase 3 owns accountless comments and principals. Phase 4 owns CRDT decode and compaction, presence, link WebSockets, and stale-generation commit pressure.

Gate: each prototype has a written pass, or a design revision recorded as an ADR update.

**Status: DONE.** Each prototype has a written pass or a phased design revision in ADR 0001, ADR 0005, or ADR 0006. The exact-head Phase 1 and Phase 2 gate passed before this disposition was recorded.

## Phase 2: View slice

The first shippable vertical: accountless viewing.

- Desktop: create, rotate, and revoke a View link from the existing share dialog. Access retuning remains unavailable until Phase 3 earns Comment. When retuning becomes available, it offers only levels whose phase gate has passed — Comment after Phase 3, Edit after Phase 4 — so no link advertises authority its safeguards have not earned. Rotate, revoke, and raising a link's level warn before running: rotation and a level raise permanently kill the old URL — and per ADR 0005 they also reach every dependent named grant created through "Open in dohc", so the warning names those recipients too; revoke ends every session and dependent grant derived from the link. The walkthrough test covers the dependent-grantee wording.
- `share-web`: secret exchange at the relay seam (ADR 0001), folder navigation, sanitized Markdown, safe images, Excalidraw view, forced download for untrusted formats. The fragment secret is exchanged by POST for a short-lived derived session capability stored in a `Secure`, `HttpOnly`, host-only cookie; the viewer then removes the fragment from the address bar and history (`history.replaceState` or equivalent), the secret never persists client-side, and the gate tests the cookie's attributes, the final address, and history state. A link secret comes from a CSPRNG with at least 256 bits of entropy, is stored only as a keyed hash, and verifies in constant time, with tests for all three properties.
- Sessions are per-link: cookie naming or a server-side session map keyed by link id keeps two links open in one browser fully distinct. The Phase 2 gate covers two different shares and two View links to the same share. Phase 3 adds mixed-level same-share coverage when Comment becomes reachable.
- Honest freshness: the viewer shows settled content with a "last settled" indicator; it never calls a stale snapshot live.
- Current-state opening: the viewer opens from a link-authorized listing with projected entries, digests, settled metadata, and a log cursor. It pages the log only for changes after that cursor.
- Refusal discipline: invalid id, bad secret, revoked, and rate-limited responses are indistinguishable before authentication.
- Owner visibility: per-link usage, and a warning that a link exposes everything under the selector — including files added later for live-follow path shares; a version share is a snapshot, so its warning omits the future-files clause. Both the creation warning and the leaked-URL walkthrough say plainly that revocation ends future access but cannot recall content already downloaded, cached, or copied — and that the relay serving the link reads the shared content in plaintext, so the secret hides the work from other people, not from the service. The self-hosting docs repeat the same fact; the dialog is where the Cloud owner actually reads it.
Settled for View: viewer metadata omits owner email, workspace ids, private ancestor paths, and participant identities. Remote media is blocked. Viewer responses use `private, no-store`. Every `share-web` response sends `X-Robots-Tag: noindex, nofollow, noarchive`; valid and invalid entry points return the same generic shell, and unfurls disclose no shared content. Chat-channel selectors remain excluded.

Gate:

- Hostile-content, refusal-oracle, revocation, and granter-ownership-loss tests pass. `serves only the different object recreated at a selected path` pins recreation; authenticated viewer responses are `private, no-store` and superseded digests refuse.
- `projects only the selected current files from a fresh view capability`, `applies the current-file cap after selector filtering and refuses overflow generically`, and `opens mature shares from current state and then follows forward updates` pin bounded current-state opening and forward replay.
- Concurrent-download tests pass; `waits for drain before pulling more and cancels the upstream body on close` pins slow-consumer backpressure and cleanup. `keeps total blob egress on the grant across rotation and refills it` pins the per-grant byte bucket; `keeps exhausted public link controls off the owner sync path` pins quota separation.
- `keeps two View tabs isolated across different and shared selectors`, `blocks a cross-origin handoff mint without disturbing the viewer`, and `renders a representative Excalidraw scene without leaving the viewer origin` pin the real-browser matrix. `keeps valid and garbage viewer entries uniformly unindexable` pins the generic entry shell and unfurl policy; `refuses and closes a streaming request as soon as it crosses the body cap` pins the same noindex contract on adapter refusals.
- `uses the 32-byte CSPRNG bearer seam for create and rotate` pins credential entropy. The leaked-URL walkthrough matches the owner-facing warning about plaintext relay access and content that recipients already downloaded, cached, or copied.

**Status: DONE.** The HTTP View slice and its phase gate are complete. Comment, live Edit, and apps remain disabled pending Phases 3, 4, and 5.

## Phase 3: Comment

- Mint link principals on first interaction; claimed names are display metadata, marked unverified.
- Enable access retuning between View and Comment. Mixed-level links to one share remain isolated, and raising a link repeats the permanent old-URL and dependent-grantee warning.
- Promoting a derived named grant warns that it is permanent: the former parent link's rotation and revocation no longer reach that grantee. The reverse path is revoking the named grant itself.
- Extend the relay's chat author contract to recognize a server-minted link principal as the authenticated pusher without weakening named-user authorship.
- One share-level discussion object; text only. No attachments, reactions, decisions, or anchored comments. Messages reach link holders through a server-side author projection that exposes only the approved display identity — never account identifiers — with a mixed named-and-link-author disclosure test in the gate.
- Owner moderation: delete comments and block principals; a single "pause all link writes" control that preserves viewing. Blocking and pausing reverse in place (unblock, resume); comment deletion warns that it is permanent before it runs. Blocking an accountless principal keeps its existing sessions bound to that principal and stops their writes without ending link reads. The UI says plainly that a determined holder can remint an identity from the same link: rotation is the durable response. The gate includes a fresh-profile remint test. Block and pause join revoke in the commit-time authority check — a buffered append from a blocked principal or paused link refuses at commit, and the gate races both transitions against in-flight appends.
- While Comments is open, the public viewer and owner dialog follow durable discussion activity. Appends, deletes, blocks, unblocks, pauses, and resumes converge without reopening the panel. Phase 3 does not add proactive notifications: no bell, toast, unread state, offline delivery, mute, typing, or presence. Later notification delivery belongs to a product-wide notification channel.

Gate: quota, moderation, and revoke-during-append tests pass; open public and owner panels converge through every discussion and moderation change; provenance shows link id and principal on every message; hostile markup, URL-scheme, and output-encoding tests cover comment bodies and claimed names, which are new attacker-controlled rendering inputs the Phase 2 gate never saw.

**Status: DONE.** The Comment slice and its phase gate are complete. Live document Edit and apps remain disabled pending Phases 4 and 5.

## Phase 4: Edit

- One configured session host per deployment (ADR 0003): the service host module for dohc Cloud and willing self-hosters; device-only mode otherwise. No automatic movement.
- Journal before acknowledgement; the session ticket is single-use, short-lived, and bound to principal, audience, workspace, version, object, lineage, grant generation, and host epoch, with replay and cross-document tests; commit-time recheck of grant, selector containment, and epoch on every accepted update.
- Durable authorship records outside the prunable Y.Doc update cache; settlement references its audit interval.
- Build the owner stop-and-restore action before exposing Edit to anyone. Grant invalidation leads the action: the sequence is revoke-or-downgrade committed at the relay first (it holds on its own — every later write refuses at commit), then fence, then restore, each step durable and idempotent so a crash or connection loss between steps resumes rather than half-applies — in device-only hosting the relay and the device cannot share one transaction, so the ordering and resumability ARE the correctness. The gate breaks the sequence at every boundary and proves recovery, and proves the old URL cannot open a session against the retained lineage the restore keeps (the settled shape restores on the same document; lineage replacement is a separate provenance scenario, tested as such). The action warns before it runs: the confirmation names the accepted post-restore-point work the restore will discard, so the owner consents to that exact loss — an implementation that restores without this confirmation fails the gate.
- Ship named-recipient browser Edit first; enable anonymous Edit only after the same path passes adversarial load with link principals.
- Named browser sessions authenticate for real: sign-in on `share-web` maps a relay-derived account identity to its named grant, never a client claim, and a cookie for one grantee never authorizes another. Without this, "named Edit first" would silently run on the anonymous link path under a different label.
- A device host maintains an authenticated outbound connection to `share-web` (registration, document routing, reconnect, and fencing over that pipe), because NAT means `share-web` can never dial the device. The gate includes a test where `share-web` cannot initiate connections.
- Presence is server-projected per principal kind: define which fields an anonymous editor receives, redact server-side, and test what an anonymous session can see of named collaborators.
- Scope: existing Markdown live documents on the main version. No create, rename, delete, Excalidraw editing, or pinned-version editing.

Settled: a desktop named recipient's live-document Edit pauses when no host is online, exactly like the browser — a proposal lane there would give Edit two meanings, which ADR 0002 and the glossary both forbid. Settle first: what the owner's local edits mean while a service host holds the session and the owner's device is offline, including which side settles on reconnect; when View joins the live Y.Doc read-only vs reads settled Markdown; settlement cadence and maximum document size.

Gate: restart, stale-frame, selector-drift, access-change, and restore tests pass under load; the stop-and-restore drill completes against a live hostile session; an attributed-update test verifies link and principal audit records survive compaction, replication, settlement, and lineage replacement; and the shipped live-session endpoint refuses WebSocket upgrades whose `Origin` is missing or unapproved (ADR 0003) — the Phase 1 prototype is throwaway, so the real endpoint proves it.

## Phase 5: apps

- Publications first (ADR 0006): immutable bundles without dohc data capabilities on isolated per-publication origins, served static. Ordinary React and React DOM remain supported design targets; app authors do not need a dohc UI framework. Browser networking follows ADR 0006's ordinary web-app trust model. Choose the build trust model here, including whether Vite's plugin surface is admissible. Every declared and build-resolved workspace input must satisfy the active share selector and path policy — a bundle can bake bytes the data API would refuse, so the check runs at publication, and the gate attempts an out-of-selector build import.
- Then owner-approved read capabilities tied to the bundle digest, delivered through the scoped data API. Settle first: the app-session credential exchange — a one-time launch handoff mints an app-scoped session bound to grant, generation, and publication, because the viewer's host-only cookie cannot cross to the app origin and the link secret must never enter JavaScript-visible app state. The handoff itself is short-lived, delivered by POST to a trusted app-origin bootstrap and exchanged for a protected host-only cookie before the bundle loads, so owner-authored code never sees a bearer; the gate includes leakage and redemption-race tests. App sessions stay distinct per link exactly as viewer sessions do — the same publication launched from two links keeps two bindings, gated with a concurrent-links test — and each app session carries its server-minted link principal, so provenance, budgets, and principal blocks distinguish two browsers on one grant (tested with two principals writing through one link). An approved capability never reaches outside the share's selector in v1: an out-of-selector dataset fails closed at approval, visibly.
- Then, only if a launch app needs it, one typed create-only collection per ADR 0004, after naming the authoritative app-data store and its sync, export, backup, restore, and deletion path — with a recovery test proving a backup reconstructs the records, their provenance, and their idempotency state on Cloud and self-hosted deployments alike.
- App mutation authority is the owner-approved capability intersected with the link grant, independent of the document level: a View link votes in an approved poll, because gating data writes on Edit would force owners to hand out document-edit authority to collect responses. The share dialog states what the approved app lets any holder do and that it may send received data elsewhere. The gate tests mutation at every level.
- Service workers, persistent storage, raw HTML, inline SVG, and remote embeds stay disabled until a specific use case passes a threat test.
- Apps may use ordinary browser networking without a separate dohc network grant. Remote script and module loading remain blocked so executable dependencies belong to the approved bundle. Before approval, the owner sees the selected data and operations and the consequence that received data can leave dohc. Before launch, recipients see that the app may contact other sites and that the viewer's remote-media privacy guarantee does not apply. Publications and capabilities have visible withdrawal paths: unpublish a publication, and revoke or narrow an approved capability. Unpublishing refuses new launches and subsequent protected app reads and writes. Every dohc data operation rechecks current authority. Loaded app code and received data cannot be recalled, and withdrawal does not promise to stop external traffic. The gate proves these refusals and notices with external networking enabled, including credential, origin, message, and workspace isolation. Closing an embedded app is a user-interface action, not network enforcement.

Gate: the Phase 1 credential, origin, storage, navigation, and message-isolation attacks pass against the real app origin model with external networking enabled; network-denial checks remain viewer requirements and are not app requirements; a capability widening attempt fails closed at the approval seam; the create-only collection survives idempotency abuse — same-key replay returns the original result, conflicting-payload and concurrent retries do not duplicate, and idempotency holds across a backup restore; per-grant quotas, concurrent writes, and rejection backpressure hold under a flooding link holder — a fresh idempotency key per write must not buy unbounded appends (ADR 0004); and the owner-visible bulk undo removes a holder's appended records end to end, with provenance and idempotency state cleaned or preserved as the store defines.

## The create-only collection contract

The collections program owns the store for ADR 0004's app-data lane: the lane's dataset is a dohc collection under a create-only grant policy (`docs/plans/collections.md`, 'The word "collection" in ADR 0004'). Phase 5 implements the policy against this contract instead of naming a store of its own. The conformance test is `apps/desktop/e2e/collection-create-only-share.spec.ts`, with relay policy tests beside `services/sync-relay/src/linkGrants.test.ts`.

- Collection path. The grant policy names one collection folder inside the share's selector. The folder's `collection.yaml` fixes the schema, and records are Markdown files with engine-minted `rec_` ids. Store, sync, export, backup, restore, and deletion ride the workspace file substrate the collection already uses; only idempotency and quota state is relay-side, and it must survive a relay backup restore.
- Create-only. The policy permits one operation: create a record that validates against the schema fixed at approval time. Authority is the owner-approved capability intersected with the link grant, independent of the share's document access level.
- Idempotency key. Every create names a caller-chosen idempotency key, scoped per grant and principal. Replaying a key returns the first result and creates nothing. A same-key retry with a different payload refuses without creating. Concurrent same-key retries produce at most one record.
- Server-set fields. The relay sets the record's principal and created timestamp; the principal is the server-minted link principal. A create body that names either field refuses. Record history attributes the create to the link principal.
- Write path. The relay accepts the create, stamps the server-set fields, and appends one moment for the record file to the owner's workspace stream; the owner's engine replays it like any synced write and mints the record id at adoption. The relay keeps the idempotency and quota state beside its grant state, restored with the relay's own backup, so a restored workspace and a restored relay agree on which creates happened.
- Quota per grant. The relay enforces a per-grant create quota with rejection backpressure. A fresh idempotency key does not refill quota. The limit is deployment configuration, never a client claim.
- Refusals. Update, delete, any write to `collection.yaml`, and any write outside the named collection path refuse byte-identical to a missing share. Update-own-row arrives only when a real app requires it (ADR 0004).

Owner moderation keeps ADR 0004's shape: append-only record history and one owner-visible bulk undo that removes a principal's created records, with provenance and idempotency state cleaned as the store defines.

## Cross-cutting

- Phase 2 documents one `share-web` instance: its public viewer domain, exact `Host` allowlist, TLS proxy, trusted-proxy client-IP rule, relay-volume backup and restore, no-cache proxy rule, log hygiene, retention, degraded behavior, and restart sign-out behavior. Horizontal scaling is unsupported in v1. Phase 4 adds WebSocket proxy timeouts. Phase 5 serves apps from a separate registrable domain and documents its `Host` allowlist, wildcard DNS, and wildcard TLS policy.
- Phase 2 applies an IP request budget before authentication, per-grant request budgets after authentication, and a per-grant byte budget to authenticated metadata, log, and blob responses. These controls are separate from owner sync. Phase 3 adds principal budgets. Phase 4 adds document, workspace, and owner aggregation for live sessions.
- "Open in dohc" is an explicit acceptance step that tells the viewer the owner will learn their identity; the desktop handoff uses a single-purpose short-lived code, never the bearer URL. This ships and gates in Phase 2 with the viewer: the gate proves identity is disclosed only after acceptance and that no desktop protocol handler ever receives the bearer URL.
- Every phase runs the repository gates that its changed paths select, per `AGENTS.md`.
