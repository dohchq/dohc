# App backends own private transactional data

Apps that reserve capacity or manage private responses need atomic rules across rows and access independent of their shared source files. Each app backend therefore owns a workspace-scoped SQLite database and owner-approved operations. Local apps commit on the owner's device; shared apps use one authoritative host, with local writes fenced before transfer. This preserves consistency at the cost of refusing shared writes while that host is unavailable.

Approved backend code evaluates against a bounded database snapshot in a fresh QuickJS Wasm child. The host commits the candidate, history, retry receipt, and file associations together after rechecking authority and revision. The snapshot design keeps app execution outside trusted service processes and makes rollback explicit, at the cost of a small database limit and copying work per operation. External effects are excluded from retriable operations.

Private backend data and uploads do not enter ordinary shared-file routes. Link, helper, and owner operations confer explicit access; table and agent edits invoke those same operations. Collections retain their Markdown-record model. This supersedes the create-only, no-files, browser-only scope in [ADR 0004](0004-writable-app-data-is-a-narrow-lane.md) while preserving explicit owner approval, immutable publication, and browser isolation from [ADR 0006](0006-apps-publish-as-approved-bundles.md).
