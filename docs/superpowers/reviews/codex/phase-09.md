### [MED] (auth-boundary) Test device-approve seam's "double gate" is effectively a single gate (NODE_ENV is never production in shipped deployment)
- FILE: services/workspace-api/src/main.ts:82-89 (gate); 22-29, 37 (secret); docker-compose.self-host.yml:69-89; services/workspace-api/package.json (dev/start scripts)
- DETAIL: The /test/device/approve seam is documented as 'Double-gated: env flag AND never in production NODE_ENV' (main.ts:50). In practice the second gate is inert: NODE_ENV is never set to "production" anywhere — the self-host compose runs `pnpm --filter @dohc/workspace-api dev` (= `tsx watch src/main.ts`) and the `start` script is `node dist/main.js`, neither sets NODE_ENV; grep confirms the only NODE_ENV references in the whole phase-9 surface are these two lines in main.ts. So `process.env.NODE_ENV !== "production"` is ALWAYS true in a real self-host, and the seam is gated ONLY by DOHC_TEST_AUTH==="1". If an operator sets DOHC_TEST_AUTH=1 by accident (e.g. copying a dev .env), /test/device/approve becomes a full impersonation endpoint: handleTestDeviceApprove signs up + signs in as ANY email taken from the request body and approves an arbitrary device code (main.ts:51-74), handing the caller a valid desktop session for any identity. Compounding it, DOHC_TEST_AUTH=1 also skips the BETTER_AUTH_SECRET length check (main.ts:24) and falls back to the source-visible constant 'dev-test-only-secret-0123456789abcdef' (main.ts:37), so every session token becomes forgeable by anyone who reads the repo. The only operator signal that this dangerous mode is live is a single non-error console.log line (main.ts:96), trivially lost in container logs. The gate fails OPEN on undefined NODE_ENV instead of failing closed.
- FIX: Make the gate fail-closed: require an explicit dev signal, e.g. `(process.env.NODE_ENV === 'development' || process.env.NODE_ENV === 'test')` instead of `!== 'production'`. Set `NODE_ENV: production` on the workspace-api service in docker-compose.self-host.yml. Refuse to start (process.exit) — not just warn — if DOHC_TEST_AUTH is set while NODE_ENV is not explicitly development/test, and never substitute the hardcoded secret in that case.

### [MED] (token-handling) Cloud credential file written world-readable (no 0600), including plaintext-token fallback
- FILE: /home/ice/dev/dohc/apps/desktop/src/workspaces/cloudCredentialStore.ts:90-95
- DETAIL: save() writes dohc-cloud.json via writeFile(tmp, ...) with no mode option, then rename()s it over the target. Node's default is 0o666 & umask, typically 0644 — readable by every local user. mkdir(dir, { recursive: true }) at line 90 likewise sets no mode. This matters most in exactly the environment where the `plain:` fallback fires (Linux/WSL without a secret service, line 81-83): the raw Better Auth session token sits world-readable on disk, and that token is a full account credential (server derives identity solely from it — services/workspace-api/src/auth/session.ts:20-25). Even the `enc:` case is weaker than it looks on Linux: Chromium's basic_text backend reports isEncryptionAvailable()=true with a hardcoded key, so file permissions are the real boundary. The atomic-rename preserves the tmp file's lax mode.
- FIX: writeFile(tmp, payload, { mode: 0o600 }) and mkdir(dir, { recursive: true, mode: 0o700 }); optionally chmod the final file to 0o600 on load() to heal existing installs. No-op on Windows, so safe cross-platform.

### [MED] (token-handling) Session token sent to whatever serverUrl the workspace registry recorded — no check it matches the server that issued the token

### [HIGH] (sync-data-loss) Binary file updates via sync/apply always fail: update op routes to saveAsset which is insert-only, permanently wedging all push sync
- FILE: services/workspace-api/src/routes/sync.ts:96-110
- DETAIL: applyOperation for op:'update' with bytesBase64 (no body) calls backend.saveAsset (sync.ts:104-109). The postgres backend's saveAsset (packages/workspace-postgres/src/services/backend.ts:116-136) calls insertAsset (packages/workspace-postgres/src/repositories/assets.ts:53-96), which is a plain INSERT with revision=1 and maps the unique violation on assets_workspace_path_unique to WorkspaceError('conflict','File path already exists'). There is NO updateAsset function in the repository. So the first local modification to any synced binary file (image, PDF, or a SQLite .db edited through Phase 8's applyDatabaseEdit) produces an update op that fails on every push, and because applyWorkspaceSync is fail-fast, every subsequent change in the workspace is blocked too — cloud sync is permanently wedged with errors only in the console. Additionally, even if insert worked, the client's expectedRevision is silently discarded on this path, so asset writes would be last-writer-wins with no two-machine arbitration. The merge-sync unit tests never catch this because their fake server upserts on update (packages/workspace-sync/src/mergeSync.test.ts:44-57).
- FIX: Add updateAsset(db, actor, {path, expectedRevision, mediaType, kind}, stored) to repositories/assets.ts that locks the live row FOR UPDATE, rejects stale expectedRevision, bumps revision, and swaps object_key; route op:'update' with bytes to it in applyOperation. Keep saveAsset create-only.

### [HIGH] (sync-data-loss) Delete op discards expectedRevision: stale delete from one machine destroys another machine's newer content, then pull removes the local copy
- FILE: services/workspace-api/src/routes/sync.ts:112-114
- DETAIL: WorkspaceSyncOperation delete carries expectedRevision (sync.ts:32) and createMergeSync faithfully sends it from the baseline (scanWorkspaceDiff, diff.ts:28-35), but applyOperation calls backend.deleteFile(actor, operation.path) dropping it; backend.deleteFile (packages/workspace-postgres/src/services/backend.ts:159-171) has no revision parameter and softDeleteAtom/softDeleteAsset perform an unconditional soft delete. Two-machine data loss chain: machine A updates notes.md and pushes (server rev 2; A's baseline records its new sha). Machine B, still on rev 1, deletes notes.md locally and pushes delete expectedRevision='1' — server deletes anyway. A's next pull: notes.md missing remotely, A's local copy is clean vs its baseline (cloudSync.ts:246-254), so A rm's it. A's newer content is gone from both machines (recoverable only by manual DB surgery in atom_revisions). The revision arbitration the merge engine relies on ('server-side revision check arbitrates') simply does not exist for deletes.
- FIX: Thread expectedRevision through deleteFile (or add a deleteFile overload used by sync) and reject with conflict when String(row.revision) !== expectedRevision, mirroring updateAtom (repositories/atoms.ts:162-163).

### [HIGH] (sync-data-loss) Soft-delete tombstones + non-partial unique indexes: deleting then re-creating any path (or renaming onto a deleted name) wedges push forever
- FILE: packages/workspace-postgres/src/db/migrations/0001_initial.sql:70-71, 109-110
- DETAIL: atoms_workspace_path_unique and assets_workspace_path_unique are plain unique indexes on (workspace_id, path) with no 'where deleted_at is null' predicate (also schema.ts:121, 159-162). softDeleteAtom/softDeleteAsset keep the row at the same path with deleted_at set (repositories/atoms.ts:188-209). Consequence: a completely ordinary flow — delete todo.md (push succeeds, tombstone remains), later create todo.md again — makes insertAtom hit the unique violation and throw 'File path already exists' (atoms.ts:137); same for assets (assets.ts:91-93) and for renameAtom/renameAsset targeting a previously-deleted name (atoms.ts:262, assets.ts:165). The push then fails on every retry (fail-fast apply), permanently blocking all sync for the workspace, and the client has no reconciliation path (see partial-apply finding).
- FIX: Make both indexes partial: unique on (workspace_id, path) where deleted_at is null (new migration: drop and recreate), or have create resurrect/replace the tombstone row inside the transaction.

### [HIGH] (sync-data-loss) refreshBaseline rescans the workspace AFTER push: edits made during the push window are marked synced, never push, and are later overwritten by pull
- FILE: packages/workspace-sync/src/cloudSync.ts:134-150, 181
- DETAIL: push() computes the diff from a scan at T0 (cloudSync.ts:169), applies it, then refreshBaseline does a FRESH local scan at T1 and records each remote file's revision paired with the CURRENT local sha256 (cloudSync.ts:141-148). Any edit landing between T0 and T1 (push includes multiple network round-trips; the watcher's queueSync explicitly fires during pushes) gets baked into the baseline as already-synced: the next scanWorkspaceDiff sees manifest sha == disk sha and emits nothing, so the edit silently never reaches the server — pendingChangeCount even drains to 0 (cloudSyncEngine.ts:79-85), reporting 'synced'. Worse, when another machine later updates that file, pull's dirty check compares localFile.sha256 to the absorbed entry.sha256 (cloudSync.ts:217), finds them equal, deems the file clean, and OVERWRITES the local edit with remote bytes (cloudSync.ts:231-241) — irreversible local data loss with no conflict file. Same root cause for deletes: a file deleted locally during the push window is dropped from the baseline by the remote∩local intersection (cloudSync.ts:139-140), so the deletion never pushes and the next pull resurrects the file.
- FIX: Never rescan for the baseline. Carry the T0 scan (sha256 per path) through from scanWorkspaceDiff, and build the new baseline from those recorded hashes plus the per-op revisions the server returns from sync/apply (it already returns files[]); list-remote only for paths the push didn't touch.

### [HIGH] (sync-data-loss) Partial fail-fast apply + baseline-only dirty check leaves sync permanently wedged with no self-healing path
- FILE: packages/workspace-sync/src/cloudSync.ts:176-183, 207-229
- DETAIL: applyWorkspaceSync is documented fail-fast and non-transactional (services/workspace-api/src/routes/sync.ts:58-70): ops before the failing one are committed. When push() throws, refreshBaseline never runs (cloudSync.ts:176-181), so already-applied updates keep stale expectedRevision in the baseline; every retry now fails at the FIRST such op with 'Expected revision is stale' (repositories/atoms.ts:162-163), and already-applied creates retry as creates and fail with 'File path already exists'. pull() cannot heal it: the dirty check (cloudSync.ts:217) compares the local sha only against the BASELINE sha, never against the fetched remote bytes — so a file whose local content is byte-identical to remote still gets a spurious <path>.conflict (cloudSync.ts:223-227) and the baseline is not advanced. Net effect: one transient mid-batch failure (network drop, oversize file, tombstone collision, quit during initial push — main.ts:177-181 hard-exits after a 3s race) converts into a permanent wedge: pending count climbs forever, repeated pulls spam identical-content .conflict files, and nothing ever syncs again without manual surgery on .dohc/sync-manifest.json.
- FIX: Two complementary fixes: (1) in pull(), when sha256(fetched bytes) === localFile.sha256, adopt the file into the baseline (revision + sha) instead of writing a conflict — this makes push wedges self-heal on the next pull; (2) make sync/apply transactional (single withTransaction around the batch) or return per-op results so the client can advance the baseline for the applied prefix.

### [MED] (sync-data-loss) Merge push does not filter *.conflict files — conflict artifacts are uploaded to the cloud and propagate to every machine
- FILE: packages/workspace-sync/src/cloudSync.ts:169, 223-227
- DETAIL: mergeSync.pull() writes remote content beside dirty files as <path>.conflict. The watcher records that write and queues a push, and push() feeds scanWorkspaceDiff output straight into sync/apply with no filtering — unlike the old client, which explicitly excluded conflict ops (packages/workspace-fs/src/syncClient.ts:288-298 isConflictOperation). So every conflict artifact is created remotely (as an octet-stream asset, since '.conflict' maps to application/octet-stream), pulls down onto every other machine, and on the next divergence can itself spawn <path>.conflict.conflict cascades. Conflict markers are meant to be local-only working artifacts.
- FIX: Filter operations whose path/fromPath/toPath ends with '.conflict' in mergeSync.push() (reuse isConflictOperation from syncClient.ts, exporting it), and skip remote *.conflict files in pull().

### [MED] (sync-data-loss) Pointing an existing baseline at a different/empty server mass-deletes clean local files; manifest has no server binding and pull has no mass-delete guard
- FILE: packages/workspace-sync/src/cloudSync.ts:246-254
- DETAIL: pull() treats every baseline entry missing from listRemote() as a remote deletion and rm's the local file when clean. The sync manifest records workspaceId but NOT serverUrl (packages/workspace-fs/src/metadata.ts:16-25), and neither push nor pull verifies manifest.workspaceId === remoteWorkspaceId. Because enable-sync claims the LOCAL workspace id on whatever server the user is logged into (apps/desktop/src/main.ts:417-448), migrating to a self-hosted server (a headline feature: docker-compose.self-host.yml, DOHC_CLOUD_URL), or any re-provisioned/reset remote DB (dev-cloud workflows), yields a fresh empty remote workspace with the SAME id while the stale baseline lists every file as previously synced — the first pull then deletes the entire clean local workspace. Compounding it: workspaceActivity.enableCloud returns early when an engine exists (workspaceActivity.ts:101), so after re-pointing the registry the old engine keeps running until restart, and the deletion lands on next app open with no warning.
- FIX: Record serverUrl (and verify workspaceId) in the sync manifest; on mismatch refuse to sync until the user explicitly re-baselines. Additionally add a tripwire: if pull would delete more than N% of baselined files, abort and surface a confirmation instead.

### [MED] (sync-data-loss) Cross-folder file moves produce a rename op the server categorically rejects — everyday `mv a/x.md b/` wedges all push sync
- FILE: packages/workspace-fs/src/diff.ts:51-64
- DETAIL: scanWorkspaceDiff pairs any delete+create with matching sha256 into a rename op regardless of directory, but applyOperation throws 'cross-folder renames are not supported by workspace sync' when dirname(fromPath) !== dirname(toPath) (services/workspace-api/src/routes/sync.ts:117-119). Moving a file between folders locally therefore generates a push that fails deterministically on every retry (the diff is recomputed identically), blocking the entire workspace's sync until the user happens to edit the file (changing its sha and breaking the pairing). Bonus hazard: pairing is by content hash alone, so deleting one empty/identical-content file while creating another unrelated one is silently misclassified as a rename.
- FIX: Only pair delete+create into a rename when dirname(fromPath) === dirname(toPath); emit delete+create otherwise (content is re-uploaded, semantics preserved). Longer term, support cross-folder renames server-side.

### [MED] (sync-data-loss) pull() dirty-detection uses a single stale scan across a long sequential network loop — an edit made mid-pull is overwritten as 'clean'
- FILE: packages/workspace-sync/src/cloudSync.ts:187, 217, 231-241
- DETAIL: pull() snapshots local files once (line 187), then performs one GET per changed remote file. With many files this loop spans seconds, and it runs exactly when users start working: engine.start() fires on app open and enable-sync (cloudSyncEngine.ts:88-95, workspaceActivity.ts:90). If the user edits a file after the snapshot but before the loop reaches it, the dirty check (line 217) compares the PRE-EDIT sha against the baseline, deems the file clean, and writeFile clobbers the user's edit with remote bytes — no conflict file, no recovery (the .dohc history may hold the change set, but the working copy is silently reverted).
- FIX: Re-hash the local file immediately before the overwrite (inside the per-file iteration) and route to the conflict path if it changed since the snapshot; or write to a temp file and rename only when the re-check passes.

### [MED] (sync-data-loss) Sync baseline is written non-atomically and initialize() silently resets a corrupted baseline to empty, cascading into conflict spam and create-wedge
- FILE: packages/workspace-fs/src/metadata.ts:36-40
- DETAIL: writeManifest is a plain writeFile — a crash or the quit path's hard app.exit(0) after the 3-second race (apps/desktop/src/main.ts:177-181; an initial push of a large workspace easily exceeds 3s) can truncate .dohc/sync-manifest.json mid-write. mergeSync.initialize() catches ALL readManifest errors — including JSON parse failures and validation errors, not just ENOENT — and overwrites the baseline with an empty one (cloudSync.ts:153-166). With an empty baseline over a previously-synced workspace, the next pull writes a spurious <path>.conflict for every file (local files are 'dirty' vs no entry) and the next push sends creates for every file, which the server rejects with 'File path already exists' — the unrecoverable wedge described in the partial-apply finding, triggered by a single ill-timed quit.
- FIX: Write the manifest via temp-file + rename (atomic on the same filesystem). In initialize(), only create an empty baseline when the error is ENOENT; rethrow parse/validation errors (or quarantine the corrupt file and force an explicit re-baseline that uses content-equality adoption).
