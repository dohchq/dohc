Ambiguities / flags for the Rust design (not blocking, but worth a human/integrator decision):
1. versions-read-binary-blob (line 5519-5529): the `workspaceId` input is asserted non-empty but never used to scope the SQL query — `binary_blobs` has no `workspace_id` column at all (it's a global content-addressed table). Cross-workspace blob reads by hash are structurally possible today if two workspaces' binary content produces the same sha256 (extremely unlikely in practice, but the isolation guarantee is weaker than every other read path in this file). Decide whether the Rust storage layer should add workspace scoping to blob storage or keep it global-by-hash intentionally.
2. versions-resolve-text-conflict (line 5691-5860): does not check `conflict.status === "open"` before proceeding — it only compares the live file head against the conflict's recorded `current` snapshot. For apply-incoming/apply-merged resolutions this accidentally fails closed on a second call (the head has already changed), but for "keep-current" (no write happens) a second call would silently re-mark the conflict resolved and re-journal a conflict.resolve op with no side effect other than the duplicate journal entry. Worth an explicit idempotency guard in the rewrite.
3. versions-run-in-engine-write-lane (line 5399-5420) and versions-open-and-validate-store are the two rows with `security_class: none` — both are internal engine plumbing/bootstrap layers with no workspace-identity check of their own; every other row enforces workspace scoping via `normalizeWorkspaceId` + `requireWorkspaceVersionRow`/`workspace-mismatch` checks. This is expected (scoping happens one layer up, in the tasks/methods that use the lane or the store), but flagging so the Rust crate boundary doesn't accidentally drop that expectation.
4. I treated `applyReplicationOp`'s six op-kinds (workspace.init, moment.append, version.create, conflict.open, conflict.resolve, ydoc.update) as six separate behavior rows plus one shared "envelope" row for the dedup/gap/ack contract, since each op-kind has materially different tables/idempotency/risk — this reads as 7 rows against one exported method. Flagging in case the granularity convention expects one row per public method regardless of internal dispatch; happy to collapse if so.
5. Line spans for multi-part behaviors (e.g. rollback, replication apply-moment-append) point at the primary implementing function(s); some also share smaller inline helper spans (e.g. duplicate-moment-id checks, `insertMomentRow`, `journalLocalReplicationOp`) that are reused across many rows and weren't separately spanned out to avoid row explosion — grep for `insertMomentRow(`, `journalLocalReplicationOp(`, `requireWorkspaceVersionRow(` in the file if the crate-graph work needs those call sites enumerated too.

## Cluster: schema

engineDbSchema.ts does not reference changeSetStore.ts or versionedFileWorkspace.ts (the quarantined legacy files) at all, so nothing here was excluded on that basis.

This file is the sole DDL owner shared by ~10 other store modules over one physical engine.db — the "proposed_home" column reflects where each table's *domain* logically belongs in the planned crate graph (storage/sync/collab/runtime/domain/crypto), but note the plan needs an explicit decision on whether the Rust rewrite keeps ONE schema-owning crate (mirroring today's single-file-owner invariant that prevented the changeSetStore/chat-store DDL drift called out in the file's header comment) or splits DDL ownership per-domain-crate with a coordination contract to avoid re-introducing that drift class.

Coverage gaps found (no direct test hit via table-name grep, worth flagging to the test-classification workstream): sync_identity table; chat_channels/chat_reactions table set specifically (channel_id column is tested via linkedChatStore.test.ts, but not the channels/reactions tables themselves); versions.sync_materialized column; chat_messages.author_user_id/parent_message_id/origin columns; moments.sync_record_only column. These may well be covered by tests in other clusters' files (e.g. syncApply.test.ts equivalents) not in my assigned file set — flagging rather than asserting absence of coverage project-wide.

All lazy-additive upgrade blocks (rows 5-19) share one structural risk not fully captured per-row: they run as a FIXED SEQUENCE of individually auto-committed statements inside initializeOrValidateEngineSchema with no enclosing transaction. A process crash mid-sequence (e.g. after ENGINE_YDOC_DDL but before ENGINE_SEARCH_INDEX_DDL) leaves a partially-upgraded schema; this is safe today only because every step is independently idempotent AND every consumer treats its own table's absence as "feature not yet used" rather than "corrupt" — a real behavioral coupling across ~15 call sites that a Rust rewrite should either preserve exactly or replace with a single transactional migration runner (a likely "seemingly insane but doable" simplification worth flagging to the plan).

Two columns (content_kind variants, ensureBinaryContentKindColumns) and three individual ALTER helpers (channel_id, author_json, sync_record_only) all reimplement the identical "PRAGMA table_info → ALTER → re-check on race" pattern; ensureNullableColumn is the generic version but the three named helpers predate it and were never consolidated. Pure simplification opportunity for the rewrite, not a behavior difference.

ENGINE_SCHEMA_VERSION has been 1 since inception per this file — there is no exercised version-bump/upgrade-from-v1-to-v2 path in this module; the only "version mismatch" behavior tested is the corruption case (any version != 1 is fail-closed corrupt, never migrated). If the Rust rewrite needs real schema-version migrations, that machinery does not exist yet anywhere in this file and would need to be designed fresh, not ported.
